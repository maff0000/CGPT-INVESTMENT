## Findings
- Creating an agent creates an individual messageable agent.
- Sending work to an agent is an asynchronous priority handoff.
- The current T-Bot identifier `81d8cf38-188e-4592-b08d-b59d6e461e83` is reused and is not modified by this record.
- Parent-reported created identifiers, not inspected by this session: E-Bot `53f42f0b-4b9e-429f-9317-6e7edf2d8e26`, S-Bot `5cddba3b-38ff-49c8-8e9b-37b63efebe3c`, R-Bot `76efa575-82b5-44c0-a0df-5647c78b0083`, M-Bot `59ccea20-1754-437f-8fa9-424ff18e5221`, NEO `e1e372c8-20e9-45a6-856f-4eabdf018308`. Handoff verification is pending.
- The text supplied when an agent is created shapes its instructions. That text is not proven to be a hard tool access-control list.
- Agents on the same box share a filesystem.
- No automatic attachment of the private Python package, and no production ledger write bridge, has been verified.
- NEO is logically read-only. A persona statement does not enforce that limit. Hard capability enforcement has to be tested.

| Source | What it supports |
|---|---|
| [Teams and enterprises](https://docs.x.ai/grok-bot/teams-and-enterprises) | Isolation is per user. Within one user, all of that user's bots share one computer. ## Supported later adapter — not implemented
The documented minimal path, not a workaround and not started here, is offline validation of typed JSON, frozen strategy and role-transition checks, one central transactional writer, and a separate immutable hash snapshot plus audit result for NEO. A shared operating system makes an interface-level read-only flag not a security boundary. Strong NEO isolation needs a separate security principal, runtime and service with its own protected boundary. That boundary is not implemented. This record does not provision it.

[Inference Hooks](https://docs.x.ai/grok-bot/inference-hooks): Enterprise beta; Cursor signs model-input `prompt` frames with a webhook HMAC; `actor.type` is always `user`; the signed object is a model prompt, not a ledger envelope and not a bot-to-bot handoff. Not adopted. The parent inspected the live handoff descriptor earlier the same day and did not call it. It accepts a target, a message, optional images, and a required priority, and returns a delivery acknowledgement. It exposes no platform-signed sender certificate. This record does not name that tool.

Parent paraphrase of the six answers in private ADR 0015:

1. Today the signed-in Cursor member owns the spool and ledger, because every Bot of that user shares one Firecracker computer. An enforceable file boundary would require a different Cursor user whose computer alone holds the live files. That user does not exist and was not created.
2. Any process that can write the spool can submit evidence. Nobody can mint a trusted attestation. `synthetic_fixture` and `simulated_inbound_handoff` are offline labels.
3. Another Bot is not prevented from modifying ledger records. SQL append-only triggers bind a connection. They do not stop a same-user process from replacing the SQLite file.
4. NEO receives an exported snapshot through a read-only evidence reader. That is API isolation. The content hash is a truncation check a same-user process can recompute. A writer user would stop NEO from opening the source ledger. A snapshot copied back onto this computer would still be writable here. Export integrity stays HOLD even after a writer user exists, until a verifier exists that Bots on the reading computer cannot mint.
5. Sender identity cannot be independently established on the documents read. A Bot has no identity of its own, and the pages do not document a Python-verifiable sender signature. Inference Hooks do not fill that gap.
6. A separate Cursor user is the documented isolation mechanism. OS accounts on this shared computer are not a documented per-bot boundary. No such principal is in force, so sender authentication and NEO isolation stay HOLD.

Both HOLDs stay. No independently enforceable principal exists today. A separate Cursor user would be a file boundary, not a sender verifier. Creating that user is not the step that sets `authenticates_sender` true or activates `parent_platform_metadata`. A live message would not prove identity either. The design rejects an HMAC or shared secret, an in-process role check, OS-account theatre, a shared Bot, `parent_platform_metadata` as proof, and a second ledger. The seven infrastructure decisions in the packet require Matt's approval and are not performed here. No native message was sent. No Cursor user, OS account, shared Bot, credential, or permission was created or changed. `authenticates_sender` stays false. `parent_platform_metadata` stays refused. Builder `Ran 152 tests` on Python 3.12.3 is a regression of the unchanged Increment B suite, not a new Increment C count, and not Architect acceptance. Python 3.9 was not installed in that builder environment. This follow-on does not accept the private head.

The Increment B section below remains the historical proposal of that increment, later accepted by REVIEW-M5-INDEP-002. The older section that leaves Increment C gated remains that historical plan. This successor does not rewrite either section.
